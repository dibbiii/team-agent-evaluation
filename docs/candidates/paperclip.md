## 1. Scopo originario e confini del prodotto

- Paperclip si presenta come "app per gestire agenti AI al lavoro": server Node.js + UI React che orchestra "una squadra di agenti per gestire un'azienda" (org chart, obiettivi, ticket, budget, governance). Slogan: "Manage business goals, not pull requests". `DOC` README.md:42-52.
- Non è nato come piattaforma di sviluppo software: l'esempio canonico è "Build the #1 AI note-taking app to $1M MRR" con ruoli CEO/CTO/CMO ecc. `DOC` README.md:52-56; ruoli agente `ceo, cto, cmo, cfo, security, engineer, designer, pm, qa, devops, researcher, general` `CODE` packages/shared/src/constants.ts:47-60.
- Confine dichiarato: "Control plane, not execution plane — Paperclip orchestrates agents; it doesn't run them". `DOC` docs/start/architecture.md (sezione "Key Design Decisions"). Gli agenti sono processi/servizi esterni (Claude Code, Codex, ecc.) invocati a "heartbeat" (finestre di esecuzione brevi). `DOC` docs/agents-runtime.md:7-18.
- Cosa risolve realmente (per il nostro caso): ticketing agentico con checkout atomico, org chart, approvazioni, budget, dashboard, routine, costi per agente. Cosa **non** è: scheduler di issue Jira, planner DAG deterministico, model gateway per task, knowledge engine con code intelligence, runtime sandbox di default (vedi §10).

## 4. Architettura

- **Stack a livelli**: UI React → API REST Express → PostgreSQL (Drizzle) → Adapter. `DOC` docs/start/architecture.md. Monorepo: `server/`, `ui/`, `cli/`, `packages/{db,shared,adapter-utils,adapters/*,plugins/*,paperclip-runner,mcp-server}`. `CODE` (ls).
- **Modello di esecuzione "heartbeat"**: un agente non gira in continuo; viene svegliato da `timer`, `assignment`, `on_demand`, `automation`; wakeup coalescenti (nessun run duplicato se già in esecuzione). Il server invoca `execute()` dell'adapter, che lancia il processo agente con variabili d'ambiente Paperclip; l'agente chiama la REST API di Paperclip per leggere assegnazioni, fare checkout, aggiornare stato. `DOC` docs/agents-runtime.md:20-30; docs/start/architecture.md ("Request Flow").
- **Stato**: tutto in Postgres: issue, commenti, documenti con revisioni, run (`heartbeat_runs`), eventi run, wakeup, sessioni task agente (`agent_task_sessions`), approvazioni, budget, costi, attività. `CODE` packages/db/src/schema/ (es. `heartbeat_runs.ts`, `agent_task_sessions.ts`, `cost_events.ts`, `budget_policies.ts`, `issue_execution_decisions.ts`, `activity_log.ts`). Log run completi su disco/store separato `DOC` docs/agents-runtime.md:105-107.
- **Eventi/UI realtime**: push live di stato agente/run/attività `DOC` docs/agents-runtime.md:109-120.
- **Adapter** (ponte verso i runtime): `claude_local, codex_local, opencode_local, cursor (+cloud), gemini_local, grok_local, kimi_local, pi_local, hermes_local/gateway, openclaw_gateway, process, http` + adapter esterni (plugin). `DOC` docs/agents-runtime.md:35-52; `CODE` packages/adapters/ (ls).
- **Plugin system** con worker out-of-process, job, tool, UI. `DOC` README.md (sezione Plugins); ROADMAP.md:11-13; packages/plugins/. Provider di sandbox sono plugin (§7).
- **Paperclip Runner (sperimentale)**: processo separato `paperclip-runnerd` (Rust) che possiede il processo provider, con protocollo PRP su WebSocket, recovery dopo interruzione; **ADR in stato "Proposed"**, dietro adapter `paperclip_runner` e flag di istanza default-off. `DOC` doc/architecture/paperclip-runner.md:1-30. Provider qualificati: Codex, OpenCode, Claude Managed, AWS AgentCore, profili ACPX Claude/Codex (il runner **non** instrada gli adapter esistenti). Stato di maturità: sperimentale.
- **MCP**: Paperclip è sia endpoint MCP (`packages/mcp-server`, `public-mcp`) sia **gateway MCP governato** (connessioni, catalogo con rischio read/write/destructive, profili, policy allow/block/require_approval/rate_limit, richieste di azione con approvazione umana, audit). `DOC` doc/MCP-ACCESS-GOVERNANCE.md (Mental model).
- **Doppia superficie legacy/native**: la documentazione interna distingue percorsi "legacy" e "native runner" con semantiche diverse di cancellazione/recovery (doc/execution-semantics.md, passim). La complessità interna è molto alta (execution-semantics.md: 2.047 righe; `issues.ts` > 11.000 righe `CODE`): costo di comprensione/manutenzione per un eventuale fork.

## 6. Ruoli, task, deleghe, DAG, scheduling, collaborazione, stato persistente

- **Org chart**: agenti con ruolo, titolo, linea gerarchica, permessi, budget. `DOC` README.md (Org Chart). I ruoli sono etichette descrittive; i permessi effettivi sono grant separati (vedi §7).
- **Issue**: singolo assegnatario (agente **o** utente, mai entrambi — "hard invariant") `DOC` doc/execution-semantics.md:24-30; stati `backlog, todo, in_progress, in_review, done, blocked, cancelled` `CODE` constants.ts:190-197; parent/sub-issue (struttura) vs **blocker** (`blockedByIssueIds`, dipendenza esecutiva) `DOC` execution-semantics.md:292-323. Un'issue con blocker irrisolti non produce run; al completamento dell'ultimo blocker scatta il wake `issue_blockers_resolved` (execution-semantics.md:319). Blocker "cancelled" non soddisfa la dipendenza (:321).
- **Checkout atomico / lock anti-duplicazione**: `checkoutRunId` + `executionRunId` con update condizionale in transazione; rifiuta checkout se blocker irrisolti o hold di pausa sull'albero `CODE` server/src/services/issues.ts:11704-11800; self-heal di lock su run terminali/mancanti (execution-semantics.md:204-215). Il checkout è lock per **run**, non lease con TTL: la scadenza dipende dalla finalizzazione/recovery del run (`CODE` issues.ts:7529-7810, adopt/clear stale checkout).
- **DAG**: il grafo è costruito **dagli agenti a runtime** con `create_task` e `set_dependencies` (idempotenza per issue sorgente + chiave chiamante); un piano accettato (documento con revisioni) autorizza l'esecuzione, e la decomposizione in figli è opzionale e decisa da una skill/guidance (`paperclip-converting-plans-to-tasks`) `DOC` execution-semantics.md:343-351. Esiste anche un'API di decomposizione "exact-once" (tabella `issue_plan_decompositions`) mantenuta come superficie di compatibilità `CODE` schema/issue_plan_decompositions.ts; execution-semantics.md:351. Non c'è un DAG dichiarativo con campi Objective/Scope/Risk/Verification/Budget per task (`UNVERIFIED` esaustivo; esiste `completion_contracts` con `risk`, `completionAuthority`, `incompleteCriteriaPolicy` `CODE` schema/completion_contracts.ts:~20-25, da approfondire) → `PARTIAL`.
- **Planning mode**: ROADMAP.md "Deep Planning (planning mode, revisioned plans, plan approvals)" ✅ `DOC`; modifiche piano con revisioni documento e approvazione `DOC`; blocco di "cambi silenziosi" non verificato (`UNVERIFIED`).
- **Scheduling**: coda di wakeup su DB con coalescing, controllo budget, risoluzione workspace (README.md "Heartbeat Execution"), timer per agente, **routine** cron/webhook/API con policy di concorrenza e catch-up che creano issue tracciate `DOC` README.md (Routines). Non è uno scheduler "smart" per priorità/rischio/risorse: la priorità esiste come campo issue, il parallelismo è limitato da assegnazione per agente e lock workspace (`workspace_busy` → attesa automatica `DOC` execution-semantics.md:272-275). `UNVERIFIED` un limite globale di concorrenza configurabile.
- **Deleghe e comunicazione**: sub-issue, commenti, menzioni, canali di report figlio→padre (completion signal, commento sul padre diretto, trust-gated) `DOC` execution-semantics.md:325-338; "Courier pattern" per coordinamento laterale (:339). Non esistono messaggi diretti agente-agente a bassa latenza: la collaborazione passa per issue/commenti/wake `DOC`. Parzialmente adatto al requisito "no chat gigante condivisa".
- **Review indipendente**: *execution policy* per issue con stage `review` e `approval`; il runtime intercetta `done` → `in_review`, assegna al revisore (esclude l'esecutore originale), registra decisioni in `issue_execution_decisions`, ciclo changes_requested → stessa fase `DOC` docs/guides/execution-policy.md:1-125. Applicato da runtime, non solo da prompt (`DOC`; `CODE` server/src/services/issue-execution-policy.ts presente). Che il revisore riceva spec+diff e non la narrativa del developer è `UNVERIFIED` (dipende dai prompt/skill).
- **Task watchdog** opt-in: agente che verifica un albero di issue fermo e ne ripristina la liveness `DOC` doc/TASK-WATCHDOG.md; execution-semantics.md:1000-1100.
- **Persistenza**: stato progetto = Postgres, non la chat; thread, documenti, run, decisioni sopravvivono ai riavvii `DOC` README.md ("Persistent work context"). Resume sessione solo per adapter che lo supportano.

## 8. Retry, checkpoint, crash recovery, idempotenza, cancellazione, timeout, budget

- **Recovery limitato**: "Bounded run recovery" — retry per fallimenti transitori supportati, mantengono l'ownership e restano soggetti a budget/approvazioni/pause `DOC` ROADMAP.md (Bounded run recovery). Costanti: continuazioni di liveness max 2 (`DEFAULT_MAX_LIVENESS_CONTINUATION_ATTEMPTS = 2`) `CODE` server/src/services/recovery/run-liveness-continuations.ts:9; riparazione disposizione max 5 (nuovo) / 2 (legacy) `CODE` recovery/disposition-repair.ts:18; recovery/legacy-continuation.ts:25; retry per modello saturo a 1 min e 2 min senza cambio modello automatico `DOC` execution-semantics.md:649-660. Esaurimento → richiede retry esplicito/azione umana ("recovery action" con owner).
- **Classificazione dei fallimenti**: presente (quota, workspace, config incompleta, saturazione modello, avvelenamento sessione) `DOC` execution-semantics.md (§5, §9; claude-local.md). Classificazione generale "test falliti → cambia strategia/modello/ripianifica": `UNVERIFIED` (delegata all'agente).
- **Crash/restart**: "stranded assigned work" — `todo`/`in_progress` agente-assegnati senza path vivo vengono ricondotti a un percorso di recupero; sweep periodico e riconciliazione all'avvio; wait di retry sopravvivono al riavvio del controller `DOC` execution-semantics.md:864-1000, :248-249. `CODE` startup-recovery (server/src/startup-recovery-state.ts, services/recovery/*). **Non testato**: S06 resta `BLOCKED`/da eseguire.

## 10. Adeguatezza al nostro caso, cosa manca, come integrare, rischio

### Posizionamento
Paperclip è un **control plane/organizzazione di agenti** con forte governance (ticket, approvazioni, budget, audit, MCP gateway, multi-utente). Non è un execution plane isolato, né un orchestratore Jira. Per il nostro schema (Control Plane + Execution Plane) può plausibilmente coprire il **Control Plane** (R05 parziale, R09, R11, parte di R12/R13), ma R01, R06, R07, R08, R10 richiedono molto lavoro o componenti esterni.

### Cosa manca / come integrarlo
1. **Issue Queue Controller Jira** (adapter custom): webhook Jira → crea issue Paperclip via REST (con idempotency key), mappa stato/PR su Jira. Si può costruire come plugin (spec Draft esiste) o servizio esterno. Rischio medio-alto: correlazione `Jira issue ↔ task ↔ run ↔ branch/PR` e ownership di stato vanno progettate (stima qualitativa, non LOC).
2. **Execution plane isolato**: usare plugin sandbox (Daytona/E2B/K8s) o adapter `http`/`process` verso un runtime esterno (es. Warren) — **non esiste integrazione pronta con Warren** (non presumere; `UNVERIFIED`). L'adapter `process`/`http`/`external adapter` è il punto di estensione.
3. **Policy no-merge e CI gate**: branch protection GitHub, token a scope minimo, review stage obbligatorio su ogni issue.
4. **Model routing per task**: da costruire (LiteLLM davanti ad Anthropic base URL via AI Connection custom `CODE` ai-provider-routing.ts) oppure override per issue; escalation non nativa.
5. **Knowledge/Context Pack**: componenti esterni (Serena via MCP, file `AGENTS.md`/`CLAUDE.md`); Paperclip fornisce solo skills/documenti/memory plugin.
6. **Hardening**: ridurre grant agente standard, vietare adapter locali non sandboxati in produzione, usare `authenticated`+`private`, rivedere `dangerouslySkipPermissions`.

### Rischi principali
- Fit concettuale: prodotto pensato per "aziende di agenti", linguaggio e default non software-engineering; si adatta ma con attrito.
- Velocità di cambiamento e dimensione (>11k righe in `issues.ts`, 2k di semantica esecuzione, doppio percorso legacy/native): costo di fork/manutenzione alto; breaking change probabili.
- Sicurezza di default (local_trusted senza login, adapter non sandboxati, skip permissions) — gate bloccante se non confinato: "esecuzione non confinabile" (istruzioni §10) è risolvibile solo con sandbox/VM esterna.
- Budget: nessun limite per issue; stop dipendente dal reporting di spesa.
- Idoneità a produzione e giudizio PoC vanno separati: PoC fattibile per governance/dashboard/approvazioni; produzione dipende da hardening e connettore Jira.
